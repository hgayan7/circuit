# Circuit v0.3.0

Circuit now executes explicitly permitted agent actions autonomously. Operators define which actions need review; built-in approval defaults no longer override a matching `ALLOW` rule.

## Changes

- Explicit matching `ALLOW` rules authorize supported actions automatically, including REST writes, model inference routes, MCP/plugin writes, merges, and native operations. All matching `DENY` and `REQUIRE_APPROVAL` rules still take precedence, regardless of order.
- Scoped access, safety checks, durable budgets, exact-payload approvals, provider preconditions, and uncertain-write no-replay behavior remain enforced. Unmatched actions keep their existing defaults. Mutating operations keep their write classification even when authorized automatically.
- A runnable movie-booking chatbot example demonstrates trusted customer consent, purchases within policy, separate review for larger purchases, and provider-status reconciliation after a lost reply. Its business-rule tests and end-to-end walkthrough run in CI. It is deterministic and fixture-only; no real tickets or payments are involved.
- The gateway toolchain is updated to Go 1.26.9 and `golang.org/x/net` to v0.60.0 to address findings from the reachable-vulnerability check. Docker builds use the patched Go image too.
- CI rehearses upgrade/rollback from the previous stable v0.2.0 binary on unchanged disposable fixture state. Cross-platform binaries target Linux/macOS amd64/arm64.

## Migration from v0.2.0

Review broad existing `ALLOW` rules before upgrading. They can now authorize writes that previously needed human review, including actions covered by target-level approval defaults such as `require_approval`, production-environment review, and payment approval thresholds.

To preserve a human-review requirement, express it as a matching `REQUIRE_APPROVAL` rule. Such a rule takes precedence over every matching `ALLOW`. Narrow autonomous allows by agent, target, and argument conditions. Guided setup continues to generate conservative review rules; adding an allow alongside an existing matching review rule still requires review.

Pause agents, back up state, and rehearse the exact configuration on a disposable copy before resuming. Configurations without matching allow rules retain their approval defaults. See [gateway policy](../gateway-policy.md) and the [upgrade procedure](../compatibility.md). The legacy proxy remains a separate first-match policy system.

The OpenAPI wire contract remains 1.0.0. This gateway release includes the unchanged compatible Python/TypeScript/Go SDK 0.2.0 archives; SDK filenames and versions need not match the gateway version. Exact downloadable artifacts are checked before the release workflow publishes them. No external package or container registries are published.

## Try the booking walkthrough

From the matching source checkout, with Go 1.26.9+ and Python 3:

```sh
python3 examples/movie-booking/demo.py
python3 examples/movie-booking/demo.py --interactive
```

See the [booking guide](../../examples/movie-booking/README.md). Customer consent is validated by the trusted fixture service, not by an agent-provided boolean. A real provider needs durable business state, authenticated customer sessions, payment authorization, and its own failure validation.

## Qualification limits

The uninterrupted 72-hour soak remains owner-waived, not completed or passed. Independent security review remains deferred. This release does not add distributed storage, SSO/MFA, a transparent model router, token/spend accounting, or production certification for arbitrary booking/payment providers. The booking example uses local in-memory fixtures and no OS/container isolation; use the separately qualified Docker/runc deployment for enforced agent routing.

Intended providers, deployment workload, email/storage delivery, and separate-host disaster recovery still require operator acceptance. Existing fixture evidence retains its recorded scope; it is not a fresh live-provider pilot for v0.3.0. See the [release checklist](../release-checklist.md).
